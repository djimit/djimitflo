# Agent rendering and current execution-summary continuation

Scope: isolated audit checkout, synthetic local SQLite/HTTP/component fixtures. No production writes or provider dispatch in these regression fixtures. Existing execution-engine regression tests were also rerun; they are not a new native-provider benchmark.

## Reproduced defects and correction

- `NlAgentFactory.createFromDescription` writes `pending_approval`; real POST returned 201 and GET returned that status. Rendering those actual API rows in the client threw `Cannot read properties of undefined (reading 'color')`. Shared status and `AgentsPage` now support pending approval, preserve unknown status labels with neutral styling, and show offline agents' explicit retirement metadata. Three component regressions failed before correction, then passed. No activation or retirement policy was changed by this UI correction.
- `EvidenceService` treated `execution_summaries` as permanent despite task/event changes. First read during approval persisted `denied`, fabricated a start timestamp from task creation, inferred policy `allow`, and lost JSON-configured executor attribution. After completion both HTTP review and export still returned the obsolete denial. Five semantic regression cases failed before correction; the existing unauthorized-access case passed.
- Summary reads now transactionally recalculate the existing materialization from task, events, evidence, approvals and file changes, retaining the original row ID and creation timestamp. Real zero duration/token values remain zero. No new store was introduced.
- Wire `started_at` is nullable. The legacy NOT NULL materialization stores an explicitly documented empty-string absence sentinel rather than a fictitious timestamp. Task status remains pending/running/paused/awaiting approval when appropriate; cancellation is not relabelled denial.
- Policy is an actual captured top-level decision or `unknown`; an assessment recommendation remains advisory metadata. An additional red-to-green regression covers the existing engine's exact approval-HOLD capture contract (`source=policy`, `evidence_type=risk_assessment`, top-level `decision`), followed by an explicit denial transition.
- Configured executor and recorded execution-event attribution are distinguished in metadata and review UI. Neither a requested Codex string nor a fabricated fixture event is native-provider execution proof. Independent review reproduced that the initial all-row approval aggregate falsely reported an old denial after a fresh grant, and treated an unrelated manual pending action as an execution HOLD. The corrected reader exposes sanitized `approval_history` separately. Current recorded execution approval uses the newest nonmanual row matching the observed/configured executor (historical rows without executor attribution remain explicitly recorded legacy decisions); any pending execution approval or actual task awaiting-approval state still dominates. Manual-only decisions do not create execution approval requirements. This summary does not validate execution input hashes or authorize dispatch; the engine remains that authority.
- The exact `queue-admission` policy evidence written by the engine after capacity wait is included. A focused red-to-green regression prevents an earlier allow from masking the subsequently captured denial.
- `ReviewPage` previously used the completed green checkmark for unrecognized/nonterminal states. Three red-to-green render cases prove neutral awaiting-approval, running and unknown states, explicit Pending, true zero duration, and configured-but-unproven executor wording.
- Standalone dashboard API declarations now match the unchanged server contracts: raw summary and `{audit_trail}`. The existing combined review envelope remains unchanged. A client regression exercises those wire shapes.
