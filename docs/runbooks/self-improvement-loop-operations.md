# Runbook: self-improvement loop operations (production)

Production: container `djimitflo-live` on `vps-agentical` (100.86.47.122), `https://djimitflo.agentical.nl`,
compose in `/srv/djimitflo/compose.yml`, environment in `/srv/djimitflo/runtime.env`, database `/data/djimitflo.sqlite`
inside the container (`/srv/djimitflo/data` on the host).

## Deploy

```bash
scripts/deploy-vps.sh <40-char-sha>            # dry run: prints the remote script
scripts/deploy-vps.sh <40-char-sha> --apply    # clone, build, chown, swap, health-wait, roll back on failure
curl -s https://djimitflo.agentical.nl/health | jq .build   # commit_matches_build must be true
```

- Use only this script. `/srv/djimitflo/deploy-agent-commons.sh` is disabled (2026-09-23): it skipped the `chown` of the
  runtime source, so `.git` stayed root-owned and every loop run failed with `WORKTREE_CREATE_FAILED ... cannot lock ref`.
- GitHub "Push on main" does not deploy.
- The script passes `VCS_REF`, `BUILD_SOURCE` and `BUILD_TIME`; `/health` reports them as `build.*`.
- Every host-mutating operator script follows the same rule: dry run by default, `--apply` to act, unknown flag fails
  (AGENTS.md "Host scripts and skills"; checked by `scripts/host-scripts-dry-run.test.mjs`).

Draft publication recovery uses `loop_runs.metadata.draft_publication` as a persisted checkpoint: maker lease, repository/base/branch, original file list, artifact digest, parent/committed SHA, phase and a five-minute publisher lease. Inspect that checkpoint and `draft_pr_failed` events when publication is interrupted; retry the existing `LoopDraftPrService.openForRun(runId)` with the **same** run ID, environment and worktree after any live publisher lease expires. The service reconciles an exact existing draft before another POST, including after a lost GitHub response; it never force-pushes or merges. At the enforced open-draft cap, reconciliation may recover an already-created draft but cannot publish a new one. Changed ownership, stopped/paused runs, changed files/heads, mismatched PR identity or unavailable reconciliation remain blocked; preserve the checkpoint for investigation rather than clearing it. The existing LOOP_DRAFT_PR_RETRY sweep uses this same checkpoint path; LOOP_PR_CI_WATCH observes CI separately and never authorizes repair. A stop cannot undo an external request already in flight, but blocks subsequent publication actions and local success settlement.

GitHub PR webhook redelivery can recover the intake-to-dispatch crash window only: the original synthetic run retains its PR/head, repository and review-runtime binding, and no review record or worker may already exist. Deliveries for the same repository/PR/head reuse that run. A stopped/paused run, changed runtime/repository, retargeted base/head ref, missing historical checkpoint or existing pending/failed review remains held; redelivery never restarts paid work or replenishes a budget. This does not add CI-event repair or a retry scheduler.

Loop `continue`/`retry` preparation returns HTTP 409 for cancelled, completed or review-ready runs and cancelled/completed/failed goals. Explicit retry of failed or interrupted runs with a live goal remains available under the existing retry budget; ordinary continue cannot reopen them. State is rechecked before worktree creation and inside the final SQLite lease/transition transaction. If an operator stops work while filesystem preparation is already in flight, the prepared worktree may remain for inspection, but no new leases or running transition are committed. Retry preparation also rechecks the current maker, root retry count and effective retry limit inside that transaction; no new reservation framework is introduced.

`BENCHMARK_SCHEDULE_MODE=on` (code: `services/benchmark-schedule.ts`). Three fixed series, one `benchmark_runs` row per run
(benchmark id, manifest sha, prompt hash, models, runtime, started/finished, tokens, AUC or pass rate with its CI, catches /
false rejects, status `ok | failed | insufficient`):

| Benchmark | When | Where it runs | Items |
|---|---|---|---|
| `sec-f1` | monthly, 1st 02:00Z | VPS host, throwaway containers on the prod image (operator runner) | 46 SEC-F1 items, `docs/research/eco/sec-f1` |
| `f1` | monthly, 1st 02:00Z | same | 40 F1-R items, `docs/research/eco/f1` (`scripts/f1-build-items.mjs`) |
| `gym-holdout` | weekly, Monday 03:00Z | in-process (read-only query) | the current holdout epoch |

Why an operator runner and not the prod container: SEC-F1 / F1 fetch upstream repos into throwaway checkouts and run a real
opencode reviewer in them; that does not belong next to the prod DB and the live loop. The remote pull-worker route (a job
for the workstation) would need the prod opencode/Ollama credentials on another host, a new job kind and new routes; it is
not built. `ponytail:` upgrade trigger: when two monthly slots in a row go overdue because nobody ran the command, move the
runner to an approved host-agent shell job.

When the stall watch reports `benchmark:due:<id>` (only while no real lease runs), on the VPS host as root:

```bash
bash scripts/benchmark-run.sh sec-f1            # dry run: prints every command
bash scripts/benchmark-run.sh sec-f1 --apply    # the run (repeat for f1)
```

What `--apply` does: `benchmark-cli.js plan` (read-only; exit 5 = a real lease runs, nothing starts) → depth-1 fetch of the prod
build (`DJIMITFLO_BUILD_SHA`; `--ref` overrides) → prepare → baseline (SEC-F1) → the reviewer (`sec-f1-run.mjs --benchmark
--role security_checker|checker --cap <BENCHMARK_TOKEN_CAP>`: the prod checker prompt and `OpenCodeExecutor`, in-memory DB,
prompt hash recorded instead of enforced) → every `--poll` s (30) `benchmark-cli.js idle`; a real lease starting stops the
reviewer and records the reason (`failed`, the slot stays due) → score → `benchmark-cli.js ingest --apply` (the only prod DB
write: one `benchmark_runs` row). The work dir is `/var/tmp/djimitflo-bench/<id>-YYYY-MM`: rerunning the same command in the
same month resumes (finished items are skipped, the token total carries over). `--opencode-auth <file>` mounts an opencode
auth file read-only when prod uses one.

## Freeze a holdout epoch from a manifest (operator only)

Never automatic. Nothing sets `DREAM_EVOLUTION_ENABLED` or `GYM_HOLDOUT_EPOCH`, and nothing starts a scheduler. The code is `holdout-manifest.ts` (`freezeHoldoutFromManifest`), `holdout-exposure.ts` (the exclusions) and the script `packages/server/src/scripts/holdout-freeze.ts`.

1. Prepare the manifest offline (schema `manifest_version: 1`; see the epoch-1 manifest). Fields:
   - `holdout_epoch`;
   - `tasks.mined[] {key, source}`;
   - optional `tasks.write_test[] {key, source}`;
   - optional `tasks.mutant {generated_at_freeze: true, proposed_tiers}`;
   - optional `calibration {mined[], write_test[]}`: frozen as role `calibration`, never deciding;
   - `holdout_size` (or `evaluation_policy.holdout_size`);
   - `manifest_sha256` = sha256 of `JSON.stringify(manifest without manifest_sha256)`, key order as written.
   Build it with the same exclusions the freeze checks (gym failures AND failed maker leases' `changed_files`), on a read-only DB copy:
   `node dist/scripts/holdout-freeze.js --build --db <copy> --repo <checkout> --epoch 1 --size 40 --tiers 3,4,5,6 [--base <old manifest>] --out <file>`.
   With `--base` it keeps the base's still-eligible tasks, lists the dropped ones with the reason, and refills mined by an every-k-th spread. A shortfall exits 3; it is never padded.
   Epoch 1 (operator 14-10) is `docs/holdout/epoch1-manifest-20261014.json` (sha256 in the `.sha256` file next to it): 40 mined (no-regression check only), 5 write_test, 40 mutants at tiers 3–6 generated at freeze (deciding, `max_per_source: 1` → 40 distinct files, design effect 1.0, power 0.80 for +30 points at p0 0.35), `HOLDOUT_SIZE=40`. Build with `--max-per-source 1`: without a cap mutantTask returns the same file at every tier.
   Mutant keys contain the checkout HEAD, so repeat the dry run on the deploy checkout right before `--apply`.
2. Back up `runtime.env` and the DB. Use `.backup` to a unique path, then run an integrity check.
3. Dry run. It opens the DB read-only and writes nothing:
   `docker exec <container> node dist/scripts/holdout-freeze.js --db <db> --manifest <file> --epoch 1 --expect-sha <sha256> --repo <deploy checkout>`.
   Exit codes: 0 = `VALID_DRY_RUN`, 2 = `REFUSED` (with the violations), 3 = `HOLD` (with the reasons).
4. Read the output. It is refused when any of these fails:
   - the schema;
   - the sha256 matches both the embedded value and `--expect-sha`;
   - the requested epoch is the manifest's epoch;
   - the size is valid and does not conflict with `HOLDOUT_SIZE`;
   - the epoch has no rows yet;
   - every task is eligible NOW. That means: it is in the mined / failure-derived pool with the same source; it is not frozen in any epoch; it is not a TG-001 key; it was never attempted in a trial; it is not dream-exposed; its source or target file is not dream-exposed; it is not derived from an exposed commit or run.

   Dream exposure is the gym failures and failed maker leases in the 24 h before each `origin = 'dream'` genome. It covers their commits, source / out-of-scope / changed files and run ids.

   It is HOLD when there are fewer deciding tasks than the size, fewer than 5 write_test tasks, or the mutant generator cannot fill the size with eligible mutants. A HOLD never freezes a smaller epoch.

   The output also carries a power report: exact one-sided McNemar, paired. Its assumptions are set with `--p0 --p1 --alpha --icc`, and task families are grouped by source file. The report is never used to size the epoch.
5. Apply with the same command plus `--apply`. It migrates, then writes every row in one transaction: the holdout rows, a `gym_holdout_freezes` provenance row (manifest sha, `frozen_at`, origin sha / version, size, counts, operator, manifest) and a hash-chained `holdout.freeze` audit event. If the audit event fails, nothing is frozen.
6. Verify (read-only):
   - `SELECT epoch, role, COUNT(*) FROM gym_holdout / gym_mutant_holdout / gym_write_test_holdout GROUP BY 1, 2`;
   - `SELECT * FROM gym_holdout_freezes`.
7. Only then, and as a separate decision, switch trials to it. Set `GYM_HOLDOUT_EPOCH=<n>`. The deciding mutants are every mutant the manifest froze (all its tiers); `DREAM_TRIAL_MUTANT_TIERS` is ignored for a manifest epoch (a warning names a mismatch).

## Failure modes seen and what they mean

**Per-lease failure cause** (no flag; record-only, L3 v2 §5 #4): every worker lease that ends `failed` or `cancelled` carries
`metadata.failure` = `{stage, exit_code, signal, exit_observed, timed_out, token_budget_hit, stderr_class, stderr_source,
cancellation_reason}` (services/lease-failure.ts). `stage` is one of prepare / deps / maker / checks / checker / verify / cancel;
`stderr_class` is a deterministic classifier over the last 4 000 characters of the runtime's stderr (missing_module, enoent,
eacces, oom, network, rate_limit, auth, npm_ci, git, tool_loop, unknown; `stderr_source = none` means there was nothing to read).
`exit_observed = false` means no child exit was seen (never spawned, remote host, raw cancel): its null exit_code/signal are
UNKNOWN, not 0. The engine path now records the child's own exit and signal (`runtime_signal`; `exit_status` stays the gate's 0/1).
Every cancel path names a `cancellation_reason` (operator_stop, operator_lease_stop, goal_ended, gym_run_settled, agent_retired,
self_healing_stale_lease, stale_timeout, deploy_restart, maker_lost_evolve_contest, superseded_by_evolve_winner,
maker_superseded_by_evolve_winner). Outcome attribution never reads it. Counts: `GET /api/health/attribution` → `failure_capture`
(stage × stderr_class; cancels with a reason; leases ended before the capture are `without_failure`).

| Symptom | Cause | Fix |
|---|---|---|
| `WORKTREE_CREATE_FAILED ... cannot lock ref` | runtime source `.git` not owned by uid 1001 | redeploy with `scripts/deploy-vps.sh` (it chowns) |
| checker/security checker: "No diff available", `insufficient_evidence` | maker added only new files; `git diff` omitted untracked files | fixed in #334 (`workingTreeDiff`) |
| goal failed `approval expired` | nobody approved within the window | infrastructure-class failure: proposal is re-scheduled (max 2, #332); approve in Approvals |
| auto-review ticks `reviewed=0` for hours | no proposal in `proposed`; all parked | check the funnel; `needs_grounding` has no consumer yet |
| `checker_dispatch_failed: CHECKER_LEASE_NOT_FOUND` | dispatch attempted before the checker lease exists | benign when the checker runs afterwards |
| TypeSafe latency ~27 s on single calls | retries/backoff right after a deploy | none; normal is 0.3–1.4 s |
| maker `exit 1` / type-check fails in the worktree | loop worktrees have no `node_modules` | makers and reviewers run `npm ci` in their own worktree (#344, #347) |
| checker `accepted` but `checker_verdict` gate fails | checker's own install rewrote `package-lock.json` → read-only contract broken | lockfile-only rewrite restored before the check (#347) |
| checker exit 1 with `external_directory … deny` | reviewer tried to read the maker's worktree | reviewers work only in their own worktree (the maker's changes are snapshotted into it) |

## Auto-deploy (J2)

`scripts/auto-deploy.sh` runs on the VPS every 10 minutes (`scripts/systemd/djimitflo-auto-deploy.{service,timer}`) and deploys
`main` only when: it differs from what runs, every CI check on it succeeded, `main` has not moved for 20 minutes
(`AUTO_DEPLOY_SETTLE_MIN`), and no loop worker is running. It runs the **host-installed** copy
`/usr/local/lib/djimitflo/deploy-vps.installed.sh` (`--local`; health wait + rollback), never the deploy script of the commit it
deploys. That copy and its record are used only when they and every directory above them are owned by root and not writable by
group or others; each is read once into a private temp dir and that copy is hashed and executed. When the commit's
`scripts/deploy-vps.sh` differs from the installed copy (or the installed copy no longer matches its record), auto-deploy pauses
with the reason in `AUTO_DEPLOY_DISABLED` until an operator has reviewed and installed it.

Preconditions (auto-deploy refuses to act otherwise, with a log line): `/srv/djimitflo` and every directory above it are owned by
root and not group/other-writable (`chown root:root /srv/djimitflo && chmod 0711 /srv/djimitflo`; `data/` inside it stays as it
is). Git in a `runtime-source-*` clone runs as the clone's owner (uid 1001), which needs to traverse `/srv/djimitflo`: hence
0711 (traverse, no listing), so keep private files in it unreadable by others (`chmod 0600 /srv/djimitflo/runtime.env*`).
`deploy-vps.sh` (also when run by hand) checks the same before any step, plus `compose.yml` (a root-owned regular file, not
group/other-writable) and `build-receipts/`; its temp dirs live in `/srv/djimitflo/.deploy-work` (root, 0700). Paths are
checked as written (absolute, no `.`/`..`, no symlink on any component) and no world-writable ancestor is accepted, a sticky
`/tmp` included. `AUTO_DEPLOY_TRUSTED_UID`, `AUTO_DEPLOY_TRUSTED_PREFIX`, `AUTO_DEPLOY_TEST_HOOK_AFTER_TEMP` and
`DEPLOY_FILE_REMOTE` are test seams: they **must be unset** on the VPS (systemd unit and root shell). Writes into `data/` are staged in `/srv/djimitflo/.auto-deploy-stage` (root, 0700, created by the script, same filesystem
as `data/`; `AUTO_DEPLOY_STAGE_DIR`) and renamed in. `python3` must be on the host.

- Install: `install -o root -g root -m 0755 scripts/auto-deploy.sh /srv/djimitflo/auto-deploy.sh && cp scripts/systemd/djimitflo-auto-deploy.* /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now djimitflo-auto-deploy.timer`
- Deploy script (first install, and after every change to `scripts/deploy-vps.sh`): review the diff, then as root on the VPS
  `scripts/install-deploy-script.sh <sha>` (dry run, shows the diff) and `scripts/install-deploy-script.sh <sha> --apply`. It
  creates `/usr/local/lib/djimitflo` (root:root 0755, `AUTO_DEPLOY_INSTALL_DIR`), refuses a dir that is not root's or is
  group/other-writable, and writes `deploy-vps.installed.sh` (0755) and `deploy-vps.installed.sh.source` (0644). Then remove
  `/srv/djimitflo/AUTO_DEPLOY_DISABLED` if auto-deploy paused for it. Without an installed copy auto-deploy refuses to deploy.
- Stop: `touch /srv/djimitflo/AUTO_DEPLOY_DISABLED` (remove the file to resume). Log: `journalctl -u djimitflo-auto-deploy`.
- Fleet drift: every run (also while paused) compares the sha256 of `/srv/event-bus/*.py` and `/srv/agent-registry/*.py` with
  `infra/{event-bus,agent-registry}/*.py` at the running commit and writes `/srv/djimitflo/data/fleet-drift.json`
  (`AUTO_DEPLOY_FLEET_SERVICES` = `name=deployed_dir=repo_path ...`); a check that cannot be made writes
  `{status:"unknown", reason}` instead. `/health.fleet_drift` lists the drifting services; `null` means unknown — no file, an
  unknown record, a record for another commit than the running one, or one older than 20 minutes (`FLEET_DRIFT_MAX_AGE_MIN`) —
  which is not the same as no drift.

## Operator push (Telegram) — UX-12 / UX-13

Both are off by default; enabling is the operator's decision. The canonical channel is the webhook bot
(`routes/telegram.ts` → `TelegramBotService`, env `TELEGRAM_BOT_TOKEN` / `TELEGRAM_ALLOWED_USERS` / `TELEGRAM_WEBHOOK_*`).
The polling gateway in `packages/telegram` (`TELEGRAM_BOTS_CONFIG`) is kept as is and does not push.

| Flag | Default | What it does |
|---|---|---|
| `TELEGRAM_PUSH_ENABLED` | off | one message per new approval with Approve / Deny / Open buttons (dedupe per approval id) |
| `TELEGRAM_PUSH_MAX_PER_HOUR` | 6 | hourly cap on approval messages |
| `TELEGRAM_PUSH_DELAY_MS` | 15000 (15 s) | TG-2 (`approval-service.ts`): wait before pushing a new approval, so one a lane rule auto-approves right after creation is skipped as decided; `0` (or a non-numeric value) pushes at once |
| `TELEGRAM_QUIET_HOURS` | unset | UTC window `HH-HH` (e.g. `22-7`) without messages |
| `TELEGRAM_TRIAGE_ENABLED` | off | needs `TELEGRAM_PUSH_ENABLED`: one message per unlabelled D5 pre-screen rejection (Correct / Wrong rejection) and per memory candidate waiting for review (Promote / Reject); each item once; taps are refused while off |
| `TELEGRAM_TRIAGE_MAX_PER_PUSH` | 3 | triage messages per 15-minute tick; triage also stays under `TELEGRAM_PUSH_MAX_PER_HOUR`, counted apart from approvals |
| `OPERATOR_DIGEST_ENABLED` | off | daily digest via the bot: counts + `/decisions` links for approvals, D5 labels, memory review, requeue candidates and open loop PRs. Its 15-min tick is scheduler `operator_digest` (`GET /api/health/schedulers`), armed by this flag or `TELEGRAM_TRIAGE_ENABLED` (the registry names one flag); it registers only when `TELEGRAM_BOT_TOKEN` is set |
| `OPERATOR_DIGEST_HOUR` | 7 | UTC hour of the digest |
| `SCHEDULER_SELF_HEAL_MODE` | shadow | P0.1 watchdog every 15 min: an armed scheduler with no tick past 2× its interval is diagnosed (`scheduler_recovery` judgment); `act` re-arms it once via its own start function (≤ 1 restart / 6 h), verifies a tick within one interval + 10 min, else quarantines it (status `quarantined`, stall `scheduler:<name>`, no further restarts); `shadow` diagnoses and escalates without restarting; `off` disables |

Buttons only work for an allowlisted Telegram id mapped in `telegram_identities` (D3) to an active user whose role holds
`approve:task`; the decision is made through the normal approval API as that user, so `SELF_APPROVAL_FORBIDDEN` applies.
Triage buttons use the same D3 rule with the permission of the web route: `write:governance` for D5 labels (written as the
same `operator_label` judgment as `/decisions`), `approve:task` for memory promote / reject (the promote records the mapped
user as the human approver). The button carries only a kind and an id (≤ 64 bytes); the id is looked up before acting, and
the action runs through the same API route as the dashboard, as that user. Unknown or unauthorised ids are refused and audited
(`telegram_access` judgments). Memory messages include up to 400 characters of the candidate's content (secret patterns redacted).
The webhook must receive `callback_query` updates (Telegram's default unless `allowed_updates` was restricted).
Privacy: message content leaves to Telegram — titles, ids, lanes, file paths in scope and aggregates; secret patterns are
redacted; no hosts or tokens. `GET /api/health/digest` (read:evidence) shows the digest as it would be sent.
