## Confirmed defects (smallest fix, failing test, risk, M1 blocker?)

1. **H8-D1 Synthetic graph presented as structural analysis, with no provenance** *(highest impact)*
   - Fix (smallest, two options). (a) Stop producing it: in `explainer-generation-service.ts:147`, return an empty graph (or `skipGraph`) when `snapshot.metadata.source !== 'code-review-graph'`. (b) Carry it: add `source: 'synthetic' | 'code-review-graph'` to `GraphSummary` (shared/src/types/explainer.ts), then in `repo-evidence-packet.ts` skip `graph_node` facts when the source is synthetic, and in `explainer-author-service.ts` replace the Architecture text with "No structural graph (synthetic placeholder suppressed)". The 91 published bundles need a re-label or re-generation (data change: operator decision).
   - Failing test today: build a bundle through `ExplainerGenerationService` with the default `RepoGraphBuilder` on a python-only fixture repo. Assert that the architecture section does not contain `Core (typescript)`, that no fact has `source_type 'graph_node'` without `source`, and that the claim verifier does not count `graph:community:Core` as resolved.
   - Risk: low (explainer-only). It would lower grounding_ratio and OpenMythos scores on re-generation.
   - Blocks M1: **yes** if M1 relies on explainer facts or grounding as evidence. Otherwise it is a separate trust fix.

2. **H9-D1 Security finding closure not bound to a retest on the right commit/deployment**
   - Fix: in `validateSecurityFindingClosure` (work-item-service.ts:472), require `closure.rescan_ref` to resolve to a DjimitSec verification (a remediation statement with `retest.vulnerable === false`) or to a `djimitsec` task receipt with `state === 'collected'` whose `commit` equals the loop's merged commit (`remediation_ref`). Also require the loop's metadata to name this work item or fingerprint.
   - Failing test: in `integration-spine-service.test.ts`, close with `rescan_ref: 'artifact:nonexistent'` and expect `SECURITY_FINDING_CLOSURE_EVIDENCE_REQUIRED`; close two findings with the same `loop_ref` and expect the second to be refused.
   - Risk: medium. Existing closure callers need real refs, and prod has 0 closures, so there is no data impact.
   - Blocks M1: **yes** for any M1 security-closure claim; no otherwise.

3. **H9-D2 DjimitSec `UNKNOWN` receipt becomes task `completed`**
   - Fix: `djimitsec-executor.ts:115` should map only `collected` → completed, and `UNKNOWN` → failed with `DJIMITSEC_SCAN_HELD` (or a dedicated `unknown` status).
   - Failing test: in `djimitsec-executor.test.ts`, a worker that returns `state:'UNKNOWN'` should make the task status not `completed`. No test covers UNKNOWN today.
   - Risk: low. The only prod row (1 of 1) would read differently.
   - Blocks M1: no, but it is a "missing observation ≠ green" violation.

4. **H7-D1 Scheduler `executing` ≠ progress; errors are invisible for 10 of 66 schedulers**
   - Fix: in those 10 call sites, move `markRun(name)` after the work and call `markRun(name, e)` in the catch. In `loop_auto_merge`, do not mark while `running`.
   - Failing test: for `startLoopAutoMerge`, `startMergeSurvival` and `startStallWatch`, make the tick reject and expect `listSchedulers()` status `failing`. Today it is `executing`.
   - Risk: low. It may surface real `failing` and `BREACHED` health in the cockpit at once.
   - Blocks M1: yes if M1 uses scheduler health as a gate.

5. **H7-D2 Sticky `failing` for guardTick-only schedulers**
   - Fix: in `guardTick`, call `markRun(name)` when `fn` resolves or returns without throwing.
   - Failing test: `guardTick('x', fn)` where fn throws once and then succeeds should end in status `executing`. Today it stays `failing`, and existing `scheduler-self-heal.test.ts:32-42` only asserts the throw.
   - Risk: low. Blocks M1: no.

6. **H7-D3 Stall watch blind for 1 h after every boot**
   - Fix: add one catch-up `tick()` (or a `setTimeout`) in `startStallWatch`, as the other schedulers do.
   - Failing test: `startStallWatch` with fake timers should call `stallWatchTick` before `intervalMs`.
   - Risk: low. Blocks M1: no.

7. **H7-D4 (observability gap) Scheduler ticks are not persisted**
   - The registry lives in memory only, and there are 0 `scheduler_recovery` rows. Unless someone queries the admin endpoint, nothing is recorded.
   - Smallest fix: record `listSchedulers()` per stall-watch tick as one judgment, or include `by_status` in `/health`. Do this only if M1 needs historical scheduler evidence.
