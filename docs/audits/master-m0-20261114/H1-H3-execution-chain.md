## Confirmed defects (smallest fix, failing test, risk, M1-blocking)

1. **Retry-maker approval swallowed → goal fails, approved work runs for nothing** (A, normal path).
   - Fix: `packages/server/src/services/loop-daemon.ts:745-750`. When the retry throws `LOOP_WORKER_APPROVAL_REQUIRED` and is not inherited, `if (this.blockForApproval(goal, run.id, 'maker')) return;` before the error reaches the best-effort catch. This mirrors the checker path at `:896`. `resumeApprovalBlockedGoals` already resumes on approve and fails on deny/expire.
   - Failing test today: a daemon test where the retry `executeWorker` throws `LOOP_WORKER_APPROVAL_REQUIRED` and `inheritableApproval` returns null should give a goal in status `blocked` with `metadata.awaiting_approval.lease_id === retryMaker.id`. Today the goal is `failed`.
   - Risk: medium (daemon control flow; the goal stays blocked until a human decides). **Blocks M1:** yes, if M1 needs a closed maker→result chain (13 of 76 retry makers in 30 d).
2. **Approval executes a task whose lease/run is already dead** (F).
   - Fix: `execution/execution-engine.ts` `handleApprovalDecision` (~:950). Before `executeTask`, if `task.metadata.lease_id` points to a lease not in `prepared`, or the run is `cancelled` or its goal is terminal, cancel the task and return `{status:'denied', reason:'worker_cancelled'}`. Optionally also cancel pending approvals in `stopLoopRun`, `evolve-selection` and the reaper.
   - Failing test today: create a loop-worker task and its approval, cancel the lease, then `handleApprovalDecision(id, true)`. The executor should not be called. Today it runs.
   - Risk: low. **Blocks M1:** no (cost leak), but it should ship together with #1.
3. **Nested spawn ledger not closed by the normal path** (H3).
   - Fix: one `AFTER UPDATE OF status ON worker_leases WHEN NEW.spawn_tree_id IS NOT NULL` trigger in `database/migrate.ts`, next to `trg_worker_lease_settles_trace`. It mirrors lease status onto `sub_agent_spawns` (`running/completed/failed/cancelled`) and sets `spawn_trees.status='closed'` when the root is terminal. Then drop the manual UPDATEs at `proof-run-service.ts:1202-1206, 1234-1238`.
   - Failing test today: `nested-spawn-loop.test.ts`, after `executeWorker(child)`, expect `spawns.getSpawnStatus(child).status` to be `'completed'`. Today it is `'prepared'`.
   - Risk: low (nested is off in prod). **Blocks M1:** no, unless M1 uses nested spawning.
4. **Grant booked as consumption; limits never reach the child** (H2).
   - Fix (two lines of change): (a) in that same trigger on settle, `consumed_tokens += actual - grant`, using `runtime_usage.total_tokens`, so the grant becomes a reservation; (b) in `loop-worker-executor-service.ts` `executeViaEngine`, for `lease.spawn_tree_id`, cap `timeoutMs` at `sub_agent_spawns.wall_budget_ms` and pass the token grant as the run's token cap (env).
   - Failing tests today: with `SPAWN_PER_DEPTH_WALL_CAP_MS=5000`, `executeWorker(child,{timeout_ms:120000})` should give `tasks.metadata.timeoutMs <= 5000`; and after settle, `tree.consumed_tokens` should equal the reported usage.
   - Risk: low (dormant feature). **Blocks M1:** no. Alternative: if nested spawning stays unused, record H1–H4 as dormant and do not build on it.
