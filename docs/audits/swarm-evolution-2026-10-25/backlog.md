# Prioritized engineering backlog

These are implementation-ready changes to existing components, not production changes performed by the audit. Evidence is retained in the [assessment](README.md) and [evidence index](evidence.md). S/M/L are relative effort, not delivery promises. Benefits are expected operational effects requiring measurement, not demonstrated causal savings.

## SW-01 · P1 · Replace misleading success/resource projections

- **Evidence/root cause, confirmed:** Swarm sums zero `agents.total_token_usage` and duration fields while worker tasks have usage. It counts raw status active as current activity. Mission Control's route calls the first and last completed booleans success rates, defaults missing cost to zero and uses runtime-level fallback tariffs. A real HTTP fixture reproduces 100%→100% with a failed middle run and no usage records.
- **Intervention/files:** `packages/dashboard/src/pages/AgentsPage.tsx`, `SwarmOverviewPage.tsx`, `SwarmMissionControlPage.tsx`; `packages/server/src/routes/swarms.ts`, `services/loop-budget-service.ts`, existing `scorecards.ts`, `cost-ledger.ts`, `resource-ledger.ts` and shared API contracts. Reuse current canonical accounting/coverage, state exact cohorts and show null/insufficient for missing observations. Relabel lifetime reported task counters. Use equal comparable windows/strata with actual denominators; preserve binary run status as a different field.
- **Alternative:** immediately label the old curve “first/last run status, estimated cost” and disclose missingness; remove the learning claim until a valid series exists. Do not invent per-model prices or fill missing agent counters by copying totals across identities.
- **Effort/dependencies/risk:** M; read-only API/page change independent of active experiment assignments. Main risks are API compatibility, mirror double counting, cross-scope aggregation and false zero-price conversion. Preserve existing auth and cost metric versions.
- **Acceptance/tests:** three-run fixture reports 2/3 cohort completion with n=3, not a 100% cohort rate; no usage is unknown cost; zero-task agent is insufficient; mixed gym/maintenance/production never silently pooled; required review/retry/sibling costs included once. Extend existing page tests, route tests and ledger tests. A screenshot verifies matching labels and values.
- **Expected impact/confidence:** prevents unsupported idle/cheap/success conclusions; high confidence. Measure correctness and steps/time to identify a costly failed swarm on fixed operator cases.

## SW-03 · P1 · Account for terminal learning without manufacturing success

- **Evidence/root cause:** 131 guarded closures exist; 29/41 seven-day completed repair runs have one, with 12 historical unclosed runs. Failed/blocked runs have outcome/failure-gap mechanisms but no universal explicit terminal-learning disposition. Successful closure's score is assurance completeness of one run, not between-task capability gain.
- **Intervention/files:** `loop-daemon.ts`, `knowledge-runtime-service.ts`, `agent-assurance-service.ts`, current loop events/work items, `continuous-learning-loop.ts` and existing read projections. Keep successful assurance closure guarded; project/record one terminal-learning disposition for eligible failed/cancelled/inconclusive cases and explicit not-applicable for housekeeping. Reconcile missing historical evidence as unknown/blocked, not backfilled passes. Relabel assurance-score deltas.
- **Alternative:** read-only coverage/reason report before adding any new event writer; retry only an existing safe idempotent closure path after its evidence is genuinely present. Do not create a second learning scheduler or auto-generate memory for every failure.
- **Effort/dependencies/risk:** M; inspect actual eligibility and existing failure consumers first. Protected verification/promotion rules remain unchanged. Risks: duplicate reflections, retry storms, certifying stale historical evidence or treating infrastructure failure as a bad idea.
- **Acceptance/tests:** success closure remains idempotent and rejects missing/changed evidence; failed run gets a negative/inconclusive disposition without successful certification; duplicate terminal event produces one disposition; cancelled run is accounted for; maintenance explicitly not applicable; no claim that score 1.0 means learned skill. Existing knowledge-runtime, continuous-learning, failure-gap and lifecycle tests plus terminal-cohort fixtures.
- **Expected impact/confidence:** closes silent feedback gaps without proposal/memory inflation; high confidence score semantics, medium confidence on how many historical runs remain eligible. Target 100% explicit disposition for the defined eligible cohort, not 100% new lessons.

## SW-05 · P1 · Attribute total quality and resource cost to configurations

- **Evidence/root cause:** GPU sampling is strong but limited to one host/device scope; job energy is attributed to consumer species, not a complete swarm configuration. Agent counters are disconnected; cloud/CPU energy and some token paths are unknown. Current reader splits overlapping GPU jobs equally and excludes some ongoing/boundary jobs. The effort controller uses a 0.3 kW heuristic with default energy weight zero.
- **Intervention/files:** `resource-ledger.ts`, `cost-ledger.ts`, `outcome-attribution.ts`, existing run/lease/assignment metadata and agent/usage/Mission Control views. Join existing canonical usage owners and job windows to configuration/run identity. Retain known-only totals, completeness, overlapping-allocation method and unassigned energy. Distinguish GPU measured Wh, prediction and whole-host unknown. Correct the existing “wall-meter” wording without inventing a wall meter.
- **Alternative:** expose existing seven-day consumer ledger and uncertainty now; add exact configuration granularity incrementally when existing IDs support it. Additional hardware metering is optional only if the decision actually requires total-host evidence; no new purchase/service is authorized here.
- **Effort/dependencies/risk:** M; SW-02 lineage and canonical cost ownership. Risks include duplicate mirrors, crediting all GPU power to concurrent swarms, excluding failed work or comparing measured local energy to unknown cloud energy as if zero.
- **Acceptance/tests:** missing usage stays null, mirror counted once, overlapping job Wh sum never exceeds sampled host Wh, gaps not bridged, boundary/running jobs disclosed, no-success denominator undefined; all roles/retries included. Existing ledger tests plus assignment/configuration join fixtures. Reconcile UI to retained independent aggregates.
- **Expected impact/confidence:** enables trustworthy tokens/Wh per independently useful result and targeted spend decisions; high confidence measurement boundary, savings unverified.

## SW-06 · P2 · Evolve topology and effort using constrained evidence

- **Evidence/root cause:** acting bandit optimizes outcome success; weighted/graded fitness, effort and allocation include shadow paths. X1 currently has no demonstrated sibling benefit. More makers can add cost without benefit, while required reviewers are part of the safety floor.
- **Intervention/files:** existing `runtime-bandit.ts`, `evolve-selection.ts`, `fitness-view.ts`, `effort-controller.ts`, `value-allocator.ts`, daemon/budget/context integration and registered study surfaces. After current readouts permit it, evaluate the smallest allowed topology, one independent alternative or bounded parallel decomposition using actual task dependencies. Use measured resource history with explicit prediction uncertainty; do not silently replace missing energy with free compute. Preserve all floors.
- **Alternative:** retain existing acting routing and display shadow recommendation/effect estimates; deterministic per-task-class rules can precede a learned controller. Do not introduce a new optimizer/learned policy before evidence justifies it.
- **Effort/dependencies/risk:** M–L, SW-04/05 and frozen-experiment ownership. Risks: feedback bias, fewer hard cases sent to a model, nonstationarity, starving exploration, confounding topology with model quality and bypassing security review. No automatic deployment is included.
- **Acceptance/tests:** same total allowed budget/required review across comparable arms; all assigned cases retained; no extra sibling when expected information gain is absent unless within registered exploration; quality non-regression and practical resource criteria registered before scoring. Positive policy requires fresh-task replication and later survival. Existing bandit, effort-floor, fitness and registered evidence tests.
- **Expected impact/confidence:** potentially reduce repeated/surplus execution at maintained quality; medium design confidence, actual magnitude unknown.
