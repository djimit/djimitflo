# Recovery after the provider snapshot rollback (2026-10-12)

The hosting provider (mijn.host) had a storage failure on its VPS platform (incident start 2026-10-12T02:21Z). It restored the
production VM from an older snapshot. This note records what was lost, and the rules for every analysis that touches the
lost window. It changes no frozen protocol rule.

## Window

| Boundary | UTC | Evidence |
|---|---|---|
| Last surviving row | 2026-10-11T04:16:22.715Z | latest timestamped row in the restored database; the boot journal ends 04:15:59Z |
| First write after the restore | 2026-10-12T16:43:39Z | earliest post-restore row |

Everything between these boundaries is **LOST/UNVERIFIED** in every table. A missing row from the window is never a zero,
never a failure and never a success. Nothing is reconstructed from Git timestamps, logs or memory.

The newest backup on the VPS and on the NAS is from 2026-10-11T03:56Z, before the snapshot. No copy of the window exists.
A consistent backup of the restored database was taken before any recovery change:
`/data/djimitflo.backup-recovery-20261012T185328Z.sqlite` (sha256 `c7c277c7122ad4b3d90bc0c413dc22b98995d82aaecf630b8d288291fa8a6cab`,
integrity_check ok, 0 foreign-key violations).

## Known consequences

- **Audit chain:** continuous in the restored database, but forked from the lost timeline at sequence 21733. Any later disk image
  collides from 21733 onward and can only be compared and reconciled record by record, never restored over production.
- **Loop draft PRs opened in the window** have no database record: #770, #786, #788, #789, #790. They are labelled
  `gap-orphan` on GitHub for human review; they are not re-linked to runs.
- **TG-001 r1:** see [TG-001_R1_INCIDENT.md](ace/TG-001_R1_INCIDENT.md).
- **Configuration:** three operator-approved `runtime.env` changes made in the window were lost and two were re-applied after the
  restore (prescreen `shadow`, `STE_001_MODE=on`; backup `runtime.env.bak-20261012a`). `TG_001_MODE` is re-enabled only for r2.

## Protocol notes for running experiments

These notes say how the existing frozen rules apply to the window. They do not change any rule.

### ACE-001 ([protocol](ace/ACE-001_PROTOCOL.md))

`ACE_001_ANALYSIS_SINCE` defaults to 2026-10-12T00:00Z, which lies inside the lost window. The restored database holds no
outcome from the window, so the effective primary window starts at the first post-restore outcome (≥ 2026-10-12T16:43:39Z).
Outcomes before 2026-10-12T00:00Z stay `delivery_invalid` as Amendment 1 already defines. No outcome is backfilled. The target
per arm and the analysis are unchanged; the experiment simply needs more calendar time.

### D5-NO ([protocol](eco/D5NO_PROTOCOL.md))

The frozen cutoff 2026-10-11T21:00Z lies inside the lost window, so every post-cutoff shadow verdict from 21:00Z until the outage
is lost. After the restore the prescreen ran in `enforce` mode from 16:43:39Z until it was set back to `shadow` (~17:5xZ, the
idle recreate); the protocol already excludes rows in enforce mode after the cutoff. The study therefore counts only clusters
whose earliest decision is a post-restore `shadow` verdict. The cutoff, minimum n, bounds and the 90-day cap are unchanged.
