## 8. L3 executive conclusion

**What works.**
- One capability is L3, now with both gates validated: governed test-writing in the djimitflo repo.
- The chain is: executed oracle → checker (F1, AUC 0.95) → security checker (**SEC-F1 KEEP, AUC 0.975**) → merge → 22/22 survived.
- SX confirms it independently: 73/73 merged test files are present and 904/904 tests pass on current main.
- Two maker species carry it: opencode at 1.29 M tokens per verified, and the workstation SLM at 0 cloud tokens.

**Where effectiveness is lost** (in order of size):
1. **Verification saturates without measuring value.** 57 % of verified changes come from the exports lane, where the tests kill on average a third of seeded mutants (opencode) or a fifth (local). 33–63 % kill none.
2. **The settlement oracle cannot produce negatives.** Every survival-based learning signal therefore cannot discriminate: Gate B, R2, allocator credit, the north star, per-species and auto-vs-human comparisons.
3. **About 44 % of attributed outcomes are non-maker noise** (reviewer and environment failures), and per-lease causes are unrecorded.
4. Supply is about 4 verified a day across 6 experiments.
5. Fleet and shadow activity has no decision consumer.

**Whether it improves.**
- No: **L4 = 0, loops closed 0/11.**
- What is trending better is *operational*, not learned: the 7-d regression rate is 29 %, versus 38.5 % over 30 d, and failure recurrence fell from 0.56 to 0.28 per week after human fixes. There is no control, so none of this counts as evolution.

**Why.** The system learns only from what it can verify by execution. Its two outcome labels are "verified" (gates passed) and "survived" (lines retained). The first is about 44 % non-maker noise. The second is constant. Neither encodes how good a test is, although the system already computes that per run (graded mutant kill) and discards it.

## 9. One prioritized next intervention: MFR-001, mutant-kill feedback retry (offline first)

**Ordering.** §3d P0 #1, #2 and #4 should go to a separate small builder in parallel. They touch `loop-service.ts` and `loop-verification-service.ts` and do not overlap with MFR-001's offline harness. The memory-holdout readout (27-10) stays as scheduled. MFR-001 must not start a production arm while the oracle population has 6 active experiments (WIP limit 4). The offline phase needs no WIP slot.

**Hypothesis (H).** When an exports-lane test fails to kill seeded mutants of its target, a single retry that shows the maker the *surviving mutants* raises the test's kill rate on a **held-out** mutant set. A plain "strengthen your assertions" retry is the control.

**Exact change.**

*Phase 1: offline, no prod change.*
- Add `scripts/mfr-001/` and `docs/research/eco/MFR-001_PROTOCOL.md`.
- Commit the protocol sha before any scored item, as SEC-F1 did.
- **Item set.** Every 30-d exports-lane maker lease with a graded score < 1 and a stored diff:
  - n ≈ 40, out of the 64 graded (P9);
  - pinned by `diff_sha256`;
  - each item re-materialised at its base commit in a throwaway worktree on the **workstation**, never in `djimitflo-live`.
- **Mutants.** `targetMutants(original, base, target, k = 6)`, which supports k > 3 (`gym-failure-tasks.ts:36-38`):
  - a seeded split into **S** (3 shown) and **H** (3 held out);
  - the original 3 prod mutants are excluded from H to avoid leakage.
- **Arms.** Randomised by `sha256(item id)`:
  - **F** (feedback): the retry prompt carries the original test, the S mutant diffs it failed to kill, and the instruction "add assertions so these fail";
  - **C** (control): the same retry budget, with "strengthen the assertions of this test".
- **Maker.** Workstation atomic@llama-router through the local llama-router: 0 cloud tokens, and the VPS is not involved. A second species (opencode glm-5.2) only if the operator approves ≤ 2 M Ollama tokens.
- **Scoring.** A deterministic script:
  - kill rate on **H** of the retried test;
  - the baseline test must still pass on the unmutated target, otherwise the item is a failure;
  - no-change, timeout and red baseline are their own classes, never counted as a pass.

*Phase 2: only if Phase 1 is SUPPORTED and an operator OK is given.*
- Add a `MFR_001_MODE=off|shadow|on` flag to the existing retry path. The graded result is already recorded at `loop-daemon.ts:675-676`, and the retry machinery is in `loop-lifecycle-service.ts:166-190`.
- Scope: exports-lane goals with killed < total, 50 % hash arm, never auto-approved beyond the current rules.
- Admitted as an experiment only when the WIP count is ≤ 4.

**Pre-registered decision rule (Phase 1).**
- Primary endpoint: mean H-kill difference F − C.
- Test: one-sided permutation test at α 0.05, plus a seeded bootstrap 95 % CI.

| Verdict | Condition |
|---|---|
| **SUPPORTED** | difference ≥ +0.15 **and** the CI lower bound is > 0 **and** F's baseline-red rate is ≤ C's + 0.05 |
| **FALSIFIED** | the CI upper bound is < +0.15 → negative-evidence entry |
| **INCONCLUSIVE** | anything else; extend once to n 80 |

**Acceptance criteria.**
- The prereg sha is committed before the first scored item.
- At least 30 items per arm are scored.
- H is disjoint from S and from the prod mutants (asserted in the harness).
- **Zero prod writes:** the row counts of `worker_leases`, `skill_outcomes` and `judgments` are unchanged, and nothing runs in `djimitflo-live`.
- No command goes from the VPS to the workstation.
- 0 cloud tokens, or ≤ 2 M with operator OK.
- The report carries the CI, the permutation p and the per-class counts.

**Evaluation method.**
- Blind, seeded order.
- Arm labels stay hidden in the harness log until scoring.
- The scorer is a deterministic vitest run; no model self-report is used.
- Results go to `docs/research/eco/MFR-001_RESULT.md`.

**Stop / rollback.**
- Abort if more than 20 % of the first 10 items are infra failures (fix the harness and record the restart).
- Abort if any H mutant leaks into a prompt (harness assertion).
- Abort if the workstation GPU is needed by the prod remote maker queue. The harness yields: it runs only when `remote_maker_jobs` has nothing queued.
- Phase 1 has no prod state, so rollback means deleting the scratch artefacts.
- Phase 2 rollback is `MFR_001_MODE=off`.

**Expected impact** (claimed only at this strength):
- **If SUPPORTED**, this is the ecosystem's first feedback mechanism with a controlled positive effect. That is L4 on the scorecard metric "learning mechanisms with CI > 0" (0 → 1).
- It improves the defect-detecting value of the lane that produces 57 % of verified output. Today, 26/64 graded exports tests kill 0/3 mutants.
- It also gives Gate B and R2 a graded endpoint that *can* fail, which addresses §5 #1.
- **If FALSIFIED**, a negative-evidence entry prevents building a prod feedback loop on a false premise. The cost is about 1–2 days of workstation GPU and 0 cloud tokens.
- No change in verified count per month is claimed.

**Why this and not an alternative.**
- R2 / Gate B amendment (rank 2): XS and worth doing as well, but it only prevents an error; it does not improve outcomes.
- P0 repairs (rank 3): correctness hardening with no measured exposure. They run in parallel.
- Memory readout (rank 4): already scheduled.
- Finding-fix on (rank 8): an operator flag, and adds supply rather than learning.
- MFR-001 is the only option that turns already-computed but unused evidence into a controlled, unit-efficient test of "feedback improves future performance". It needs no new verifier, repo, framework or autonomy.
