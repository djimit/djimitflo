# MCP / A2A / agent-surface security gaps in Djimitflo

Reviewed 2026-10-22 against origin/main `fc29222c` and read-only prod probes (see OUR_SURFACE.md for the evidence).
Best-practice baseline:
- MCP spec revision **2026-07-28**, its Authorization section and the Security Best Practices page;
- A2A v1.0.1 §7, §13;
- OWASP MCP Security Cheat Sheet;
- OWASP Top 10 for Agentic Applications 2026 (ASI01–ASI10).

Severity is for Djimitflo **as deployed today**. "Latent" means the code path exists but no prod deployment reaches it.

## BLOCKING findings

| ID | Blocking for | Why |
|---|---|---|
| **S0** | **(a)** the G4.3 external pilot and any repository whose content the operator does not control; **(b)** giving makers any new MCP server, A2A peer, skill or retrieval source | A maker is the server: same container, same uid, `/data` readable. Every new input to a maker is a path to the prod DB. |
| **S3** | G5.1 value-linked fleet outcomes, and turning bus events (roborev findings, discoveries) into maker work automatically | Anyone on the tailnet can publish any event as any source. |

Neither is blocking for today's operation on the operator's own repository: no exploitation evidence, and no untrusted content source feeds makers yet. **Nothing found here is a live, remotely exploitable secret leak.** L3 P0-1 (federation env exfiltration) and P0-2 (`okf_get` traversal) are already fixed on main (#914).

## Checked against the best-practice list (task step 4)

| Concern | Djimitflo today |
|---|---|
| OAuth 2.1 / RFC 9728 / RFC 8707 audience | **Not implemented**. The HTTP MCP transport takes API JWTs with no audience claim (S7). It is acceptable only because HTTP MCP is not deployed. |
| Token passthrough | Yes. `tools/platform.ts:9-15` forwards the caller's token, and `explainer.ts:55-60,294-299` uses the server's token for a caller (S2 fixed for run; `explainer_ask` remains, read-only). |
| Confused deputy | S2 (fixed) and S8. |
| Tool poisoning / rug pull | We consume no third-party MCP server in prod. The operator's own MCP server is mutable build output (S11). Tool definitions are not hashed. |
| Prompt injection via tool output | Maker inputs: issue and roborev text (S3), memory rules (S14), swarm context from Qdrant (`context-injection-service.ts`), Commons text (S15). The decisive issue is S0. |
| Over-broad scopes | Every prod user is admin (S12). A federation peer would need admin on the receiver (`S/routes/federation.ts:190`, A2A.md A2A-3). |
| Unpinned `npx @latest` | `.vscode/mcp.json:6` (S9). Prod has no npx-launched MCP. |
| Auto-approve lists | None in the repo. `opencode.json` has `edit: allow`, `skill: ask`, `task: deny`, and **no `bash` rule** (opencode default: allow). The `/mcp-permissions` "allowed" rows are display-only (S5). |
| Session hijack | The HTTP transport binds a session to its principal (`http.ts:96-99`); it is not deployed. |
| SSRF | Sidecar probes and OpenAPI sync fetch DB-stored URLs (admin-registered) (`S/routes/mcp.ts:116`, `governance.ts:419,574`). The outbound guard is a denylist (S18). |

## What this PR changes

1. **S1:** `packages/mcp-server/src/tools/governance.ts`. The three `apply: true` paths require `manage:config`.
2. **S2:** `packages/mcp-server/src/tools/explainer.ts`. `explainer_create_task` and `explainer_run_task` require `write:governance`.
3. **S4:** `packages/server/src/routes/knowledge.ts`. `POST /publish` requires `write:claim`.
4. `packages/mcp-server/src/auth-context.ts`. A shared `requireMcpPermission` helper (the same table as the API).

Tests:
- `packages/mcp-server/src/__tests__/mcp-write-permissions.test.ts`: new; 2 of 3 cases fail on main.
- `packages/mcp-server/src/__tests__/explainer-tools.test.ts`: callers now run as admin.
- `packages/server/src/__tests__/knowledge-routes.test.ts`: real auth middleware; the new case fails on main.

Prod effect today: **none for current accounts**, because all 4 users are admin (S12). The fixes close the gap for the stdio VIEWER principal and for any future least-role account.
